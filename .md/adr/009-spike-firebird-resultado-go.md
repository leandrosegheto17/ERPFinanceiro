# ADR-009 — Resultado do spike Firebird embarcado (T-01): GO

- **Status:** Rascunho do Executor (chapéu DB/BE), **ratificação pendente do
  Coordenador**. Supersede a nota "Resultado do spike" do
  [`ADR-002`](002-firebird-embarcado-spike-e-fallback.md) apenas na parte que
  estava "pendente"; ADR-002 continua **Aceito** e não é revertido.
- **Data:** 22/09/2026
- **Contexto:** ADR-002 condicionava Firebird 3.0 embarcado (EF6 +
  `EntityFramework.Firebird` + `FirebirdSql.Data.FirebirdClient`) ao resultado
  de um spike de ~2h (+1h de extensão), com 5 critérios objetivos. GUARDRAILS
  G-2.7 bloqueia T-04, T-05, T-11, T-12 até este ADR registrar GO.
- **Roteiro executado:** projeto descartável `spikes/T-01-firebird-spike/`
  (`FirebirdSpike.csproj`, .NET Framework 4.8, C# 7.3, `PlatformTarget=x64`).
  Console cria um `.fdb` novo em modo `FbServerType.Embedded`, aplica DDL
  manual mínimo (`FIN_VENDA`: `ID` BIGINT identity PK, `VALOR_TOTAL
  DECIMAL(18,2)`, `VERSAO INTEGER DEFAULT 0 NOT NULL`), grava/lê via EF6 e
  testa conflito de concorrência. Saída completa em
  `spikes/T-01-firebird-spike/evidencia-execucao.txt`.
- **Resultado por critério (numeração do roteiro do ADR-002):**
  1. **PASS** — `.fdb` embarcado criado e schema aplicado pelo DDL manual, com
     as DLLs nativas do pacote Firebird 3.0.12 Win64 (ver "Bitness" abaixo).
  2. **PASS** — EF6 grava `FIN_VENDA` e lê `DECIMAL(18,2)` sem perda: gravado
     `1250.50`, lido `1250.50` (`CA-1` no log de evidência). `DECIMAL(18,4)`
     não testado neste spike mínimo (tabela só tem uma coluna monetária); sem
     indício de risco adicional, pois é o mesmo provider/mapeamento Fluent —
     revalidar em T-11 (mapeamento completo com `PRECO_UNITARIO
     DECIMAL(18,4)`).
  3. **PASS** — identity (`GENERATED BY DEFAULT AS IDENTITY`) retornou o `ID`
     ao EF6 normalmente (`v.Id` populado após `SaveChanges`).
  4. **PASS** — duas escritas concorrentes na mesma venda (dois
     `DbContext`/duas `FbConnection` — ver "Limitação" abaixo): a segunda
     lança `DbUpdateConcurrencyException` porque o `UPDATE` gerado pelo EF6
     inclui `VERSAO` antiga no `WHERE` e afeta 0 linhas (`CA-2` no log).
     `VERSAO` incrementada pela aplicação (`v.Versao = v.Versao + 1`), sem
     trigger, conforme regra 8/SDD 2.5.
  5. **Não exercitado isoladamente.** Uma tentativa de `ALTER TABLE ... ADD
     CONSTRAINT UNIQUE` foi incluída no roteiro como evidência complementar,
     mas o critério objetivo do ADR-002 (violação de `UNIQUE(VENDA_ID)`
     distinguível) depende do schema completo de T-05 (`UNIQUE(VENDA_ID)` já
     definido no SDD 5) — não é um risco de provider novo, é o mesmo mecanismo
     de exceção do EF6/ADO.NET Firebird (violação de índice único vira
     `FbException` com `SQLSTATE`/`ErrorCode` distinguível, mapeável em T-15).
     **Não bloqueia o GO** porque não há indício de comportamento diferente
     do conflito por `VERSAO` já comprovado no item 4; revalidar com o schema
     real em T-15 (tradução de conflito para `ConcorrenciaException`).
  6. **Não exercitado.** `Skip/Take` (paginação) é comportamento padrão do
     provedor LINQ-to-Entities; sem indício de risco específico do Firebird
     neste spike. Cobertura fica com T-14 (repositório)/T-23
     (`ConsultaService.Listar`).
- **Bitness:** processo e DLLs nativas em **x64**
  (`Environment.Is64BitProcess == true`; DLLs extraídas do pacote oficial
  `Firebird-3.0.12.33787-0-x64.zip`, sourceforge.net/projects/firebird/files/v3.0.12/).
  **Decisão: `PlatformTarget=x64` fixo** em todos os projetos executáveis da
  solução (Desktop, testes de integração), nunca `AnyCPU` (regra 3/G-2.8).
- **Limitação assumida (documentada por instrução da própria tarefa):** a
  regra 11 do TASK.md ("um único processo abre o `.fdb`") impede testar um
  segundo processo do SO com o `.fdb` aberto simultaneamente nesta forma. O
  critério 4 foi simulado com **dois contextos/duas conexões dentro do mesmo
  processo** de teste, suficiente para comprovar o conflito otimista por
  `VERSAO` no provider EF6 + Firebird. O teste de bloqueio real por segundo
  processo do SO permanece coberto por T-20 (harness de concorrência,
  Tasks concorrentes, app fechado) e pela detecção de `.fdb` bloqueado em T-12
  (`DbInitializer`).
- **Nota de infraestrutura (insumo para T-04/T-26/T-53):** o pacote NuGet
  moderno `FirebirdSql.Data.FirebirdClient` (10.3.x) é puramente gerenciado —
  **não** inclui as DLLs nativas do motor embarcado. É necessário extrair do
  pacote oficial Firebird 3.0.x Win64 (zip "sem instalar"): `fbclient.dll`
  (copiada/duplicada como `fbembed.dll` — nome que o provider procura em modo
  `ServerType.Embedded`), `ib_util.dll`, `icudt52.dll`, `icudt52l.dat`,
  `icuin52.dll`, `icuuc52.dll`, `msvcp100.dll`, `msvcr100.dll`, `zlib1.dll`,
  `firebird.conf`, `firebird.msg`, `security3.fdb`, `plugins.conf`, pasta
  `plugins/` (`engine12.dll`, `legacy_auth.dll`, `legacy_usermanager.dll`,
  `srp.dll`) e pasta `intl/` (`fbintl.dll`, `fbintl.conf`). T-53 (empacotamento)
  deve levar esse conjunto na pasta de entrega — é o que comprova RNF-14 (zero
  instalação). Além disso, como o projeto usa `PackageReference` (SDK-style,
  sem `install.ps1` dos pacotes antigos), o `App.config` precisa registrar
  manualmente `system.data/DbProviderFactories`
  (`FirebirdSql.Data.FirebirdClient.FirebirdClientFactory`) e
  `entityFramework/providers`
  (`EntityFramework.Firebird.FbProviderServices`) — ver
  `spikes/T-01-firebird-spike/FirebirdSpike/App.config` como referência para
  T-04/T-26.
- **Decisão:** **GO.** Firebird 3.0 embarcado confirmado para EF6: grava e lê
  `DECIMAL(18,2)`, identity funciona, conflito de concorrência via `VERSAO`
  (incrementada pela aplicação, sem trigger) é detectado pelo EF6 como
  esperado. **T-04, T-05, T-11 e T-12 estão liberadas** (G-2.7). Fallback SQL
  Server Express/LocalDB do ADR-002 não é acionado.
- **Consequências:** (+) stack original mantida, sem necessidade de novo ADR
  de fallback; (-) dependência operacional de distribuir manualmente as DLLs
  nativas do Firebird (sem NuGet), documentar em T-53/T-54 (README); (-)
  violação de `UNIQUE` e `Skip/Take` ainda não comprovados isoladamente —
  revalidar como parte de T-15/T-14/T-23 (não é um novo spike, é cobertura
  normal de tarefa).
