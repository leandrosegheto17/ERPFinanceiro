# Nota sobre a "DIVERGÊNCIA DE PRECISÃO" observada acima (não bloqueante, achado desta tarefa):
# A primeira resposta de quitação devolve `dataQuitacao` com a precisão de tick do .NET (até 7
# dígitos de fração de segundo, ex. "946492" ou "4401994"), valor calculado em memória no
# instante da quitação. Ao repetir a mesma quitação (cenário 2), o serviço relê a Venda do banco
# antes de decidir que já está Quitada (idempotência, RN-04/Venda.Quitar()) e o valor de
# DataQuitacao devolvido nessa segunda resposta já passou por um round-trip pela coluna
# TIMESTAMP do Firebird, que só armazena 4 dígitos de fração de segundo (100 microssegundos) —
# por isso a string bruta difere nos últimos dígitos (ex. "946492" vira "9464") mesmo
# representando o MESMO instante gravado (diferença < 0,1 ms nas duas execuções acima, muito
# abaixo da tolerância de 1 ms usada pelo harness para distinguir "mesmo instante com precisão
# truncada" de "quitação genuinamente nova"). Isto NÃO é uma violação do critério de idempotência
# P-2 — a prova definitiva e inequívoca de "sem novo histórico" é a contagem de VendaHistorico
# consultada diretamente no banco (2 -> 2 nas duas execuções), não a string bruta de
# dataQuitacao. Registrado aqui como observação, sem alteração de código (fora do escopo desta
# tarefa de QA) — mesma disciplina de T-37 ("observação registrada sem alterar código").
